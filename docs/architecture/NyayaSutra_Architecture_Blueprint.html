1. Executive overview

NyayaSutra AI is a legal research and case-analysis workspace for Indian lawyers. A lawyer searches the law, opens a private case workspace, uploads case papers and asks questions. Every answer must point to a passage the lawyer can open and check.

The central engineering rule is that the model proposes and deterministic code verifies. Models plan, read and write. Ordinary code decides who may see what, calculates dates, checks that every cited section exists in the sources, and blocks unsupported output. The system assists a lawyer and never gives legal advice or makes a legal decision.

4. High-level architecture diagram

  1. All traffic reaches one application. The browser has no route to the database, storage or model.
  2. Authorization runs before any data access, and row-level security repeats the check inside the database.
  3. Fast work runs in the request; slow work (OCR, embedding, translation, drafting) becomes a job row.
  4. The orchestrator picks a tool, retrieval gathers evidence, the model writes, and verification checks the result before it is shown as final.
  5. Every text sent to the model passes one masking point in llm.py.

7. Document ingestion and processing pipeline

Form of the dataWhat it isExampleWhereWhy kept separately
Raw documentExact uploaded fileFIR_123.pdfPrivate bucketThe evidential original; never altered; hash proves integrity
Extracted textText per page, including OCRPage 2 textdocuments and derivativesCan be regenerated with a better OCR
Structured metadataFacts about the documentType, language, page count, hashPostgres columns and JSONFiltering, access rules, display
ChunksMeaningful passages"Section 302", "paras 12–15"chunksThe unit retrieved and cited
EmbeddingsNumbers describing meaning384 float valueschunks.emb, memory indexFinds meaning without matching words; useless to read, cheap to rebuild

Chunking by family. Statutes split per section, judgments by numbered paragraph, contracts by clause, templates by heading, everything else by sentence with overlap. A citation therefore points at a real legal unit.

Formats. PDF, Word, Excel, CSV, PowerPoint, OpenDocument, RTF, text and images. Up to 60 pages of OCR per document by default. Long scanned bundles need this limit raised with a dedicated worker.

Multilingual documents. OCR reads a page in English first, then applies a Devanagari model to unsure lines. Hindi and Marathi text is stored, displayed and translated with consent. Search quality for these languages is weaker because the embedding model is English-only.

Authority hierarchy

Sources are ranked, never treated as equal. Web results already use tiers: official, legal publisher, news and reference, and unknown sites are dropped. The law ranking below is PLANNED as an explicit signal in reranking.

RankSourceRule
1Constitution of IndiaOverrides all other sources
2Central and state statutes in forceEffective on the date of the facts
3Rules, regulations, notificationsValid only under their parent act
4Supreme Court judgmentsBinding under Article 141; larger benches prevail; overruled cases flagged
5High Court judgmentsBinding within the state's subordinate courts, persuasive elsewhere

Freshness, amendments and history

  • Each planned section version carries valid_from, valid_to, amended_by, source and retrieval date.
  • A question asks two things: what the law is today, and what applied on the incident date. Today provisions.py already flags conduct before 1 July 2024 before applying BNS, BNSS or BSA.
  • Old versions stay searchable and labelled, because old cases need old law.

9. GraphRAG internal working

Status. Stages 1, 2, 5, 6 and 8 of the pipeline below exist as hybrid RAG. Stages 3, 4 and 7 are the planned graph work.

Conventional RAG compared with GraphRAG

Question typeConventional RAGGraphRAG
"What does Section 138 say?"ExcellentNo gain; the graph is skipped
"Where was the accused on 12 March, across all statements?"Returns the passages that look most similar and can miss oneWalks person → events → date, collecting all of them
"Which witness contradicts the FIR?"Depends on both passages reaching the top 8Compares claims about the same event
"Is this judgment still good law?"Text search for later mentionsFollows citation edges to overruling cases
"Summarise the prosecution's whole case"Sees only a few chunksUses cluster summaries of the whole case

Plain retrieval finds passages that resemble the question. Legal analysis often needs passages connected to each other that look nothing like the question. The graph supplies those connections, and the text evidence stays the only thing the model may cite.

  1. Vector-based retrieval: exact cosine search over query embedding, filtered by permitted cases.
  2. Entity-based retrieval: names, sections and dates in the question are matched to graph nodes.
  3. Graph traversal: from those nodes, follow allowed edge types with a hop limit, so the search cannot wander.
  4. Relationship-aware retrieval: each edge reached returns its evidence spans, which become candidate passages.
  5. Cluster summaries: groups of tightly connected events are summarised in advance. They help understand broad questions but are never cited; the model cites the underlying passages.
  6. Hybrid fusion: RRF combines ranked lists by position, so differing score scales do not matter.
  7. Context assembly: de-duplicate, respect 16,000 characters, group by document, keep labels.
  8. Evidence ranking: cross-encoder relevance, then authority, date validity and OCR confidence.

Contradiction detection, specifically

  1. Extract atomic claims: who, what, when, where, with a page span.
  2. Group claims by resolved event and person, using the graph.
  3. Compare with deterministic rules first: different dates, times, places, or numbers.
  4. Send only the remaining pairs to the LLM, labelled contradiction, compatible or unclear.
  5. Show both quotes side by side. The system says "these statements differ", and the lawyer decides whether it matters.

Communication. Agents never message each other freely. A central orchestrator holds one typed state object (question, plan, evidence, findings, issues), and each step reads and adds to it. Limits: 6 model calls, 2 retries and a time budget per request, with every step recorded in the answer trace.

Orchestration. Keep the current Python orchestrator while the flow stays simple. Adopt LangGraph when Evidence Analysis needs branching, checkpoints or a pause for human review, because those features would otherwise be rebuilt by hand. Long agent runs should execute through the existing job queue.

Keeping stores in step

  • Postgres is the source of truth. Everything else can be rebuilt from it plus object storage.
  • Today the app reloads the index from chunks.
  • With external stores, use a transactional outbox: the change and its "update the index" event commit together, and a worker applies it and can safely repeat.
  • Deletion must reach every store, and a nightly reconciliation check confirms that it did.

The app and jobs can run on several instances because the queue uses SKIP LOCKED. Three parts block this today: the in-memory vector index, the in-process rate limiter and the local web cache file.

Questions your mentor is likely to ask

QuestionAnswer
Why use a relational database if we have a graph?Accounts, permissions, jobs and audit need strict transactions. The graph describes content; Postgres governs the system.
How do we prevent hallucinations?We reduce them, and cannot promise zero. Layers: answer only from delimited sources, deterministic citation checks, case register lookup, a model audit, and abstaining when evidence is weak. The benchmark shows 74%, so work remains.
How do we handle outdated laws?Commencement and repeal data flags BNS vs IPC by date today. Planned section versions answer both current law and law on the incident date.
How do we manage conflicting documents?We keep both, cite both and label the conflict. The system never silently chooses one. The lawyer decides.
Can one lawyer reach another's case?The API checks membership, the database repeats it with row-level security, workers recheck before running, and tests attempt the access. Vector filtering is still application-level until pgvector.
How do we handle thousands of documents?Durable queue, background workers and batches now; OCR worker pool, pgvector and read replicas later. A single case of thousands of pages needs testing we have not yet done.
What are the bottlenecks?OCR on CPU, LLM latency, retrieval on large filters, RAM for the index, graph extraction cost.
What drives cost?Model tokens, especially graph extraction; OCR compute; storage; web search; human review time.
How do we reduce latency and cost?Skip retrieval for simple intents, use the fast model for planning and audit, cache results, extract once per document, and compare pairs only after grouping them by event.

18. End-to-end technical journey summary

  1. Enter. The lawyer registers, verifies e-mail, enrols MFA and receives a server-side session. BUILT
  2. Organise. Creating a case makes a permission boundary that the API and database both enforce. BUILT
  3. Ingest. Files are checked, stored privately, queued, read, OCR'd where needed, chunked and embedded. BUILT
  4. Understand. Today, documents are summarised one at a time. Next, entities, events and claims are extracted with page evidence. PARTIAL
  5. Connect. The case graph joins people, events and evidence, and links them to the law graph. PLANNED
  6. Ask. The planner reads the question and selects tools under a strict allow-list. BUILT
  7. Retrieve. Five rankers fuse and rerank today; graph traversal adds connected evidence. PARTIAL
  8. Reason and verify. The model writes only from delimited sources, then code and an audit model check each citation. BUILT
  9. See. Timelines, graphs and the contradiction matrix render verified records. PLANNED
  10. Deliver. Drafts export today; case reports follow, with sources attached. PARTIAL
  11. Close. Retention rules delete on schedule, and audit records remain. PARTIAL

In one sentence: NyayaSutra AI turns case papers and Indian law into connected, permission-protected evidence, and a lawyer can check every statement it makes against a source before relying on it.

NyayaSutra AI assists qualified legal professionals. It does not give legal advice or make legal decisions. All output needs review by a responsible advocate.
